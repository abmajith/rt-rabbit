# rt-rabbit — 5-year open RISC-V real-time SoC plan

*Deep-research report, 2026-11-04. 103 research agents, 21 sources fetched,
93 claims extracted, 25 adversarially verified (3 votes each), 22 confirmed,
3 refuted. Raw machine output: [`2026-11-04-deep-research-raw.json`](2026-11-04-deep-research-raw.json).*

**Decision taken after the report (2026-11-04):** start with **OpenHW CV32E40P**
as the baseline core, but keep the whole software/verification stack
core-agnostic (see [`rtl/cores/README.md`](../../rtl/cores/README.md)).

> Items marked **(general knowledge)** were *not* covered by the verified
> evidence and must be checked before you rely on them.

---

## 1. What the verified evidence says

1. **Cores.** For an MCU-class core, **lowRISC Ibex** (2–3 stages) and **OpenHW
   CV32E40P/X** (4 stages, in order) are the strongest bases. Ibex at 3 stages
   matches CV32E40P on CoreMark (1390 vs 1406) at ~40 % less area (43 vs 72 kGE,
   TSMC 65 nm, 2021 RTL). CV32E40P reached TRL-5 for RV32IMC, interrupts and
   debug at 100 % code coverage, but its F and Xpulp extensions were not
   verified. **CV32E40X** carries the CV-X-IF coprocessor port; OpenHW says
   CV32E40S/X are mature but not actively developed toward their TRL goal.
   [CARRV'21](https://carrv.github.io/2021/papers/CARRV2021_paper_8_Gallmann.pdf),
   [core-v-cores](https://github.com/openhwgroup/core-v-cores)
2. **FPGA SoC framework.** **LiteX** already integrates Ibex and CV32E40P for
   bare-metal and RTOS work (CI boots its BIOS on both in `litex_sim`), and uses
   **VexRiscv SMP** as its best-tested 32-bit Linux path. Toolchain: GCC via
   `litex_setup.py --gcc=riscv`; clang works for the 32-bit cores.
   [LiteX wiki](https://github.com/enjoy-digital/litex/wiki/CPUs)
3. **Vector units.** **Ara2** is the main open RVV 1.0 reference, hosted by CVA6;
   the authors note CVA6's issue rate limits performance on short and medium
   vectors, which is bad for low-latency robotics kernels.
   [arXiv 2311.07493](https://arxiv.org/html/2311.07493v2).
   **Spatz** is the better template for us: a compact vector unit on the small
   Snitch core over an *extended* CV-X-IF with its own wide memory port.
   [ICCAD'22](https://ar5iv.labs.arxiv.org/html/2207.07970)
4. **Verification gaps.** Verilator runs upstream UVM 2017 since Oct 2025, but
   cannot do SDF-annotated gate-level simulation, and concurrent-assertion and
   coverage support is partial. Gate-level simulation with timing is exactly
   where our time goes.
   [Antmicro](https://www.antmicro.com/blog/2025/10/support-for-upstream-uvm-2017-in-verilator),
   [Verilator docs](https://verilator.org/guide/latest/languages.html),
   [DVCon](https://dvcon-proceedings.org/wp-content/uploads/90555.pdf)
5. **GPU simulation has open starting points.**
   **RTLflow** compiles Verilog to CUDA via Verilator, ~40× *batch* throughput on
   NVDLA with 65 536 stimuli ([paper](https://tsung-wei-huang.github.io/papers/icpp22-rtlflow.pdf)).
   **NVIDIA GEM** maps a synthesized netlist (AIG) onto a virtual Boolean
   processor on the GPU, Apache-2.0, 5–40× claimed ([repo](https://github.com/NVlabs/GEM)).
   **Jacquard** (formerly ChipFlow/Loom) builds on GEM and adds Liberty delays,
   SDF back-annotation, setup/hold checks, X-propagation, and SKY130 / GF180 /
   IHP SG13G2 support on CUDA, HIP and Metal ([repo](https://github.com/ChipFlow/Loom)).
   All speedups are the authors' own; Jacquard publishes no benchmark and its
   timing accuracy is unverified.
6. **Fabrication changed in 2025.** Efabless shut down (March 2025). Tiny Tapeout
   moved to **IHP 130 nm open process** (TTIHP25a/b, TTIHP26a, TTIHP0p4 in 2026);
   **sky130 came back via ChipFoundry** (TTSKY26a/b). Keep the design PDK-portable.
   [TT news](https://tinytapeout.com/news/efabless-shutsdown/),
   [sky130 confirmed](https://tinytapeout.com/news/sky130-confirmed/),
   [TTIHP25a](https://tinytapeout.com/runs/ttihp25a/)

**Not covered by verified evidence:** riscv-formal, SymbiYosys, cocotb, RISCOF /
riscv-arch-test, Spike/Sail, riscv-dv, LLVM RVV intrinsics/autovectorization,
Vicuna, OpenROAD/OpenLane 2/LibreLane, GF180, wafer.space, Essent,
Arcilator/CIRCT, Verilator multithreading, Zephyr, PREEMPT_RT, cyclictest, WCET.

**Refuted (0–3) — do not rely on without re-checking:** the CVA6 family's stage
count and features as stated against the core-v-cores README; Spatz being only
Zve32x and lacking reductions; specific limits of Verilator coverage.

## 2. Recommended architecture

```
                 ┌──────────── SoC (own OBI/Wishbone fabric, later LiteX) ──────────┐
 Zephyr / RTOS → │  rabbit_cpu  (one port contract, many adapters)                  │
                 │   A: CV32E40P  ← chosen baseline, 2026-11-04                     │
                 │   B: Ibex / CV32E40X  (comparison; E40X brings CV-X-IF)          │
                 │   C: rabbit5 — own 5-stage, timing-predictable core              │
                 │  coprocessor port ──► "rabbit-vpu": Zve32x subset + int8/int4 MAC │
                 │  Timers · PLIC/CLIC · rt-rabbit IP (PWM, QEI, telemetry)         │
                 └──────────────────────────────────────────────────────────────────┘
 Linux / PREEMPT_RT → separate track on VexRiscv-SMP / VexiiRiscv in LiteX (reuse, don't build)
```

- **One contract, several cores.** Everything above `rtl/cores/` sees only
  `rabbit_cpu`. Adding a core = adding an adapter + file list. CI runs the same
  firmware and tests on every core in a matrix.
- **Coprocessor attach on CV32E40P (general knowledge — verify):** CV32E40P has
  no CV-X-IF. Options are (1) its internal APU interface (used for the FPU),
  (2) a memory-mapped accelerator on the bus (simplest, core-independent,
  higher latency), or (3) a CV32E40X adapter for the CV-X-IF path. Plan: start
  with (2) because it works with *any* core, and measure the latency cost; that
  measurement itself is a real-time result.
- **Own core (rabbit5)** is the research vehicle: fixed latencies, no
  speculation, measurable interrupt latency, so `rma_analysis` predictions can
  be checked against RTL, FPGA and silicon.
- **Linux:** reuse an existing core. A Linux-class core with vectors is a
  5-year project by itself.

## 3. Tool stack

| Layer | Choice |
|---|---|
| RTL | SystemVerilog, Verilator- and Yosys-compatible subset (Yosys via sv2v or yosys-slang) |
| Testbenches | cocotb + Verilator + pytest + `uv` |
| ISA compliance | riscv-arch-test via RISCOF; Sail/Spike as reference models *(general knowledge)* |
| Lockstep | RVFI trace vs Spike, instruction by instruction *(general knowledge)* |
| Formal | riscv-formal for rabbit5; SymbiYosys for bus/peripheral/coprocessor-handshake properties *(general knowledge)* |
| Random instruction streams | riscv-dv, or our own Python generator |
| FPGA | LiteX + Yosys/nextpnr (open boards), Vivado where needed |
| ASIC | LibreLane → Tiny Tapeout (IHP), later a full shuttle; PDK-portable (sky130 / GF180 / IHP) |
| Firmware | C (Zephyr, bare metal); GCC first, LLVM for vector intrinsics |
| New tools | Python for orchestration; Rust for performance-critical code (fits GEM/Jacquard) |
| Real-time analysis | `rma_analysis` (predicted) vs zyclictest on Zephyr / cyclictest on Linux (measured) |

## 5. Five-year timeline

| Phase | Goal (exit criterion) |
|---|---|
| **Y1 H1** | Monorepo + CI (**started 2026-11-04**). CV32E40P SoC in simulation → in LiteX on FPGA running Zephyr with the PWM/QEI/telemetry IP. RISCOF passing on CV32E40P. Measured interrupt latency vs `rma_analysis` prediction. |
| **Y1 H2** | rabbit5: pipelined 5-stage RV32I → RV32IM + Zicsr; passes RISCOF, Spike lockstep, riscv-formal to a set depth; boots Zephyr in simulation. First **Tiny Tapeout IHP tile** to learn the flow. |
| **Y2** | Coprocessor port in the contract. First rabbit-vpu: int8 dot-product/MAC + a small Zve32x subset; LLVM intrinsics or inline asm; int8 control/perception kernel with a fixed worst-case latency. Parallel regression runner (`tools/regress`) — first tool contribution. |
| **Y3** | Linux track: VexRiscv-SMP/VexiiRiscv with PREEMPT_RT on FPGA; cyclictest vs Zephyr. Gate-level flow on the post-layout netlist; **benchmark Icarus vs Jacquard on a real RISC-V netlist** (no published comparison found — possible paper). |
| **Y4** | Full MCU SoC tapeout on an IHP or sky130 shuttle (rabbit5 + VPU + RT IP). GPU / multi-process gate-level verification tool: extend Jacquard (batched stimuli, coverage, failure triage). |
| **Y5** | Silicon bring-up. Worst-case timing measured on silicon vs FPGA vs RTL vs analysis. Publish the end-to-end "verifiable real-time RISC-V" story. |

## 6. Where new tools add value

1. **Gate-level regression at scale:** shard across CPU cores first, then GPU
   batches on GEM/Jacquard. Clearest gap; open starting points exist.
2. **Timing-aware verification:** formal/simulation proofs of worst-case
   interrupt and instruction latency on rabbit5, fed into `rma_analysis`.
   Few open projects connect RTL verification to schedulability analysis.
3. **Coverage closure for custom vector instructions**, since Verilator's
   coverage support is weak.

## 7. Open questions (to research and decide by experiment)

1. Current CVA6 (CV32A6/CV64A6) configuration, stage count and Linux status;
   CVA6+Ara2 vs VexRiscv/VexiiRiscv as the Linux-plus-vector base.
2. Which open RVV unit (Vicuna, Spatz, reduced Ara) fits an MCU-class core over
   a coprocessor interface with Zve32x/Zve64x; maturity of LLVM RVV
   autovectorization for int8/int4 kernels on such subsets.
3. Accuracy and speed of Jacquard's SDF-annotated gate-level simulation vs Icarus
   or commercial sign-off on a real post-layout RISC-V netlist; where a new
   multi-process or GPU tool adds most.
4. Cost, cadence and area limits of IHP SG13G2/sg13cmos5l, ChipFoundry sky130 and
   wafer.space shuttles for a full SoC in 2026–2028.
5. *(added after choosing CV32E40P)* Best coprocessor attach on CV32E40P: APU
   interface vs memory-mapped vs moving to CV32E40X for CV-X-IF.

## Appendix A — verified findings (verbatim from the research run)

**Summary:** The 22 verified claims support a plan in layers. For the MCU-class core, use lowRISC Ibex or OpenHW CV32E40P/X: both are mature SystemVerilog cores with 2–4 pipeline stages that LiteX already integrates. For the Linux-capable path, use VexRiscv SMP on LiteX. Both run the standard RISC-V GCC toolchain, and LiteX says clang works for the 32-bit cores. For vectors, Ara2 (RVV 1.0, hosted by CVA6) is the main open reference. Spatz shows how to attach a compact vector unit to a small scalar core through the CORE-V X-Interface, which fits a custom int8/int4 robotics accelerator block. For verification, open tools now cover most needs: Verilator runs UVM 2017 as of late 2025. They still fall short on timing-annotated gate-level simulation and on full assertion and coverage support. GPU simulators (RTLflow, NVIDIA GEM and its derivative Jacquard, which adds SDF/Liberty timing and open-PDK support) are reusable open bases for the user's planned multiprocessing/GPU verification tool, a new tool that would make a real contribution. For silicon, the open-ASIC shuttle landscape changed sharply when Efabless closed in 2025. Tiny Tapeout moved to IHP SG13G2, and sky130 access later returned through ChipFoundry. The 5-year plan should therefore aim for IHP or sky130 tapeouts through Tiny Tapeout/ChipFoundry-style shuttles and keep the design PDK-portable.

### A.1 (high confidence, vote 3-0 (merged claims 0,1))

For the MCU-class core (3–5 stages), Ibex and CV32E40P are the strongest bases. Ibex is a 2-stage RV32E/I[M]C core with an optional 3rd (writeback) stage. Configured with that stage plus a single-cycle multiplier, it matches CV32E40P on RV32IMC CoreMark (1390 vs 1406, 2.81 CoreMark/MHz) with about 40% less area (43 vs 72 kGE, TSMC 65nm). CV32E40P is a 4-stage RV32IM[F]C_Xpulp core whose RV32IMC, interrupt and debug features were verified to 100% code coverage, with an OBI memory interface.

*Evidence:* Peer-reviewed CARRV 2021 paper by lowRISC/ETH authors; 3-0 votes on both claims. Caveats: the comparison is from 2021 RTL and the base ISA only (Xpulp gives CV32E40P an edge on DSP code), and the -1% fmax figure is relative to Ibex's own 2-stage configuration.

*Sources:* <https://carrv.github.io/2021/papers/CARRV2021_paper_8_Gallmann.pdf>

### A.2 (high confidence, vote 3-0 (claim 2))

The OpenHW CVE4 family (CV32E40P, CV32E40S, CV32E40X) are 4-stage, in-order 32-bit MCU cores. CV32E40Pv1 reached TRL-5, but its F and Xpulp extensions were not verified. CV32E40Pv2 is listed as very close to TRL-5 and has not reached it. CV32E40S and CV32E40X are described as mature but not in active development toward their TRL goal. CV32E40X is relevant because it carries the CV-X-IF coprocessor interface.

*Evidence:* Primary OpenHW README, 3-0. The 'not in active development' footnote applies to S and X, not to P. The claim that the CVA6 family is 6-stage and Linux-capable was refuted 0-3 against this source, so CVA6 details must be rechecked against CVA6's own documentation before use.

*Sources:* <https://github.com/openhwgroup/core-v-cores>

### A.3 (high confidence, vote 3-0 (merged claims 3,4,5))

LiteX gives a ready FPGA SoC path for both core classes. Ibex (RV32IMC) and CV32E40P (RV32IMC[F]) are supported as SystemVerilog CPU types without Linux, suitable for bare-metal and RTOS work, and LiteX CI boots its BIOS on both in litex_sim. VexRiscv SMP (RV32IMA[FD]+MMU, SpinalHDL, 1–8 cores) is the main and best-tested 32-bit Linux path (Linux-on-LiteX-VexRiscv). The documented toolchain is GCC installed with litex_setup.py --gcc=riscv, and the only LLVM statement is that clang works for the 32-bit cores.

*Evidence:* Primary LiteX wiki, 3-0 on all three claims. Zephyr support on Ibex or CV32E40P inside LiteX is inferred from BIOS support, not tested directly. Other Linux-capable cores exist (NaxRiscv, VexiiRiscv, 64-bit options).

*Sources:* <https://github.com/enjoy-digital/litex/wiki/CPUs>

### A.4 (high confidence, vote 3-0 (merged claims 6,7))

For the vector unit, Ara2 (pulp-platform/ara) describes itself as the first fully open-source vector processor to support frozen RVV 1.0, which makes it the leading reference. It is coupled to CVA6 as scalar host. Coherence works through a write-through CVA6 D-cache, with vector stores invalidating cache lines. The authors note that CVA6's issue rate limits performance on short and medium-length vectors, which matters for low-latency robotics kernels.

*Evidence:* Primary Ara2 paper, 3-0 on both claims. 'First' is the authors' own priority claim. Exact instruction coverage is listed in the repo's FUNCTIONALITIES.md, which was not checked. Ara2 targets application-class designs, not an MCU.

*Sources:* <https://arxiv.org/html/2311.07493v2>

### A.5 (high confidence, vote 3-0 (claim 8))

Spatz is a template for a compact vector or accelerator block on a small scalar core. It attaches to Snitch through the CORE-V X-Interface (CV-X-IF), which the authors extended so the accelerator can make its own (wider) memory accesses. Snitch only pre-decodes vector instructions and dispatches them with their scalar operands. This is the model to follow for a custom int8/int4 quantized-NN block attached to a CV32E40X-style core.

*Evidence:* Primary ICCAD 2022 paper, 3-0. PULP repositories use a Snitch-specific variant of the accelerator interface, not the exact upstream CV-X-IF spec. The claim about Spatz's Zve32x subset and missing features was refuted 0-3, so its ISA coverage needs a direct check.

*Sources:* <https://ar5iv.labs.arxiv.org/html/2207.07970>

### A.6 (medium confidence, vote 2-1 (merged claims 9,10))

Open-source verification gaps: (a) As of 2023, no open simulator could compile the full SV UVM library, and the DVCon workaround was Verilator plus UVM-SystemC. Verilator has since supported upstream UVM 2017 (Oct 2025), with UVM 2020 and complex testbenches still future work. (b) Verilator is cycle-based, so timing simulation, back-annotated (SDF) gate-level netlists and clock-less logic need another tool. Its support for concurrent assertions and coverage is still partial in the current documentation. --timing in Verilator 5 adds delays and events but not SDF.

*Evidence:* Primary DVCon paper, split votes (2-1 each). Verifiers corrected the time-sensitive part with 2025 Antmicro/CHIPS Alliance announcements and the current Verilator guide. A narrower claim about the limits of Verilator coverage was refuted 0-3.

*Sources:* <https://dvcon-proceedings.org/wp-content/uploads/90555.pdf>, <https://www.antmicro.com/blog/2025/10/support-for-upstream-uvm-2017-in-verilator>, <https://verilator.org/guide/latest/languages.html>

### A.7 (high confidence, vote 3-0 / 2-1 (merged claims 11,12,13,17,18))

GPU-accelerated RTL simulation has reusable open bases. RTLflow (ICPP 2022, a fork of Verilator) transpiles Verilog to CUDA kernels by way of Verilator's AST and optimization passes. It simulates many stimuli in parallel, and on NVDLA with 65,536 stimuli one A6000 ran about 40x faster than an 80-thread CPU baseline. NVIDIA's GEM (Apache-2.0, DAC 2025) instead synthesizes the design to an AIG and maps the netlist onto a virtual manycore Boolean processor on the GPU, much like an FPGA emulator. It reports up to 5–40x speedup over unnamed leading CPU simulators.

*Evidence:* Peer-reviewed primary papers and repos, mostly 3-0 (the GEM mechanism claim was 2-1 only because of the 'gate-level' inference). RTLflow's 40x is batch throughput, not single-test latency, and it is pinned to an old Verilator. GEM is zero-delay and functional, needs CUDA, and has a one-time synthesis/mapping cost. Its speedup figures are the authors' own.

*Sources:* <https://tsung-wei-huang.github.io/papers/icpp22-rtlflow.pdf>, <https://github.com/NVlabs/GEM>

### A.8 (medium confidence, vote 3-0 (merged claims 14,15,16))

Jacquard (formerly ChipFlow/Loom, now under the gpu-eda org) builds on GEM and goes further toward the user's netlist-verification need. It simulates RTL and gate-level netlists on GPUs (CUDA, HIP, Metal) with Liberty cell delays, SDF back-annotation, setup/hold violation checks and X-propagation. It has built-in support for SKY130, GF180MCU and IHP SG13G2. It repeats the 5–40x speedup claim, but the repo publishes no benchmark data.

*Evidence:* Single primary source (the project's own README), 3-0. Timing-model accuracy against sign-off simulators is undocumented. It is not a formal GitHub fork. The README lists limitations: edge-triggered logic only, latch handling, and clock-gate cell requirements. This is the most direct prior art for a GPU-assisted gate-level verification tool and could be extended or benchmarked rather than rebuilt.

*Sources:* <https://github.com/ChipFlow/Loom>

### A.9 (high confidence, vote 3-0 / 2-1 (merged claims 19,20,21))

The open-ASIC shuttle landscape: Efabless (chipIgnite/MPW sky130 shuttles) shut down in March 2025. Tiny Tapeout paused TT10 and its sky130 shuttles, and TT09 silicon was stuck at SkyWater. Tiny Tapeout moved to IHP's open 130nm process after two experimental runs. Later TTIHP25a/25b, TTIHP26a and TTIHP0p4 (2026) shuttles followed, and sky130 returned through ChipFoundry (TTSKY26a/b).

*Evidence:* Primary Tiny Tapeout posts, corroborated by press (Tom's Hardware, EE Times Japan). Votes 3-0, 2-1 and 3-0. The paused-sky130 state was temporary and must not be read as current. The newest IHP run is labelled sg13cmos5l rather than SG13G2.

*Sources:* <https://tinytapeout.com/news/efabless-shutsdown/>, <https://tinytapeout.com/news/sky130-confirmed/>, <https://tinytapeout.com/runs/ttihp25a/>

## Appendix B — refuted claims

- (0-3, https://github.com/openhwgroup/core-v-cores) The OpenHW CVA6 family (CV32A60AX, CV32A60X, CV64A60AX) consists of 6-stage, in-order application-class cores (RV32IMCA / RV64IMCADF) with M, S and U privilege modes for Unix-like OS support and CV-X-IF coprocessor support, making it the Linux-capable reference.
- (0-3, https://ar5iv.labs.arxiv.org/html/2207.07970) Spatz implements only the embedded integer Zve32x subset of RVV 1.0 (8/16/32-bit integer elements). At publication it lacked vector reductions and scatter-gather, so it was not yet fully Zve32x-compliant.
- (0-3, https://dvcon-proceedings.org/wp-content/uploads/90555.pdf) Verilator's functional coverage supports only cover property (assertion syntax), not covergroups. Code coverage offers only code and toggle metrics, merged across identically parametrized modules, so per-instance analysis is impossible. Exporting to lcov loses information.

## Appendix C — caveats

Coverage is uneven: the verified claims do not cover several research questions. No claims survived on: riscv-formal, SymbiYosys, cocotb, RISCOF/riscv-arch-test, Spike/Sail, riscv-dv; LLVM RVV intrinsics and autovectorization; Vicuna; OpenROAD/OpenLane 2/LibreLane, GF180 or wafer.space; Essent, Arcilator/CIRCT, Verilator multithreading; and Zephyr, PREEMPT_RT, cyclictest, WCET or timing-predictable microarchitecture. Recommendations in those areas rely on general knowledge, not on this verified evidence. Three claims were refuted: CVA6 family stage count and features, Spatz's Zve32x subset, and Verilator coverage limits. Do not rely on those details without checking them again. Several sources are dated: the 2021 core benchmarks, 2022–2023 papers and the March 2025 shuttle status. The shuttle and Verilator-UVM situation changes quickly. All GPU-simulator speedups are figures reported by the authors, under best-case or batch conditions. Jacquard's timing accuracy is unverified. Some verdicts were split 2-1 (UVM/Verilator gaps, GEM's gate-level suitability, TT09/TT10 status).
